# Dev Docs — the default doc set, one command

Every app repo carries a small set of living docs that agents and humans need to understand what is being built. This skill creates them if missing and refreshes them from the CURRENT code if present. Always derive from code, never from memory or the old doc — schemas and architecture drift.

## The doc set

| Doc | Location | Generate when |
|---|---|---|
| `database-design.md` | app root (the app owning migrations) | repo has a DB (migrations/, schema.rb, prisma/, models with SQL) |
| `architecture.md` | repo root | always for apps/services; skip for single-file scripts |
| `project-conventions` skill | `<repo>/.claude/skills/project-conventions/SKILL.md` | always |
| `README.md` | repo root | check only — flag staleness, don't rewrite unasked |
| `.env.example` | wherever `.env` lives | check only — flag vars present in code/.env but missing from example |

## Workflow

1. **Resolve root + inventory.** `git rev-parse --show-toplevel` (else cwd). Detect: DB? (migrations, schema files) · multi-service? (docker-compose, multiple manifests) · stacks (composer.json, pyproject.toml, package.json, go.mod, Cargo.toml). List which docs exist already.

2. **database-design.md** — **REQUIRED SUB-SKILL:** invoke `database-design-doc`. It handles create-vs-update and preserves `## Manual Notes`. Skip (and say so) if no DB.

3. **architecture.md** — build from real sources: README claims verified against code, docker-compose services, route/entry files, codegraph if indexed. Structure:

   ```markdown
   # Architecture — <name>
   > Generated by dev-docs on <date>. Sources: <files read>.

   ## System diagram
   (mermaid flowchart: services as boxes, arrows = real calls/data flow, label ports/protocols)

   ## Services & responsibilities
   (table: service · stack · port · role · owns-what)

   ## Data flow
   (the 1-3 flows that define the system, e.g. "config publish → invalidate → runtime reload")

   ## Boundaries & contracts
   (who owns which tables/files; shared interfaces; source-of-truth files)

   ## External dependencies
   (third-party APIs, proxies, infra — and what breaks when each is down)

   ## Manual Notes
   <!-- preserved on regeneration -->
   ```

   On update: regenerate all sections from code, carry `## Manual Notes` over verbatim.

4. **project-conventions skill** — if missing, create with: exact stack versions from manifests, exact run/test commands from READMEs/Makefile/scripts, ownership rules, naming, gotchas. If present, refresh stack/commands to match current manifests; **append** new gotchas, never delete existing ones (they are hard-won).

5. **README / .env.example** — read-only check. Report: README commands that no longer work, env vars referenced in code but absent from `.env.example`. Fix only if the user asks.

6. **Report.** One table: doc → created / updated / unchanged / skipped(reason), plus anything flagged in step 5. Suggest committing the docs (do not commit yourself).

## Rules

- **Code is the source of truth.** Read manifests/migrations/entry points before writing a single doc line. A wrong doc is worse than none.
- **Idempotent.** Running twice with no code changes = no diff (except timestamps).
- **Preserve human content.** Every generated doc has a `## Manual Notes` section that survives regeneration verbatim.
- **Skip honestly.** No DB → no database-design.md; say "skipped: no migrations found" rather than inventing one.
- **Scale the effort.** Small repo → short docs. Don't pad a 3-file CLI into a 5-section architecture doc.
